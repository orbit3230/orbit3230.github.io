# 정보처리기사
## 서버 프로그램 구현
### 62. 개발 환경 구축
#### [1] 개발 환경 구축
- **개발 환경 구축** : **개발 프로젝트를 이해하고 소프트웨어 및 하드웨어 장비를 구축하는 것**

<br>

#### [2] 하드웨어 환경
- 클라이언트의 종류 : 개인용 컴퓨터(PC), 모바일 등
- 서버의 종류
  - 웹 서버(Web Server)
  - 웹 애플리케이션 서버(WAS; Web Application Server)
  - 데이터베이스 서버(DB Server)
  - 파일 서버(File Server)

<br>

#### [3] 소프트웨어 환경
- 시스템 소프트웨어의 종류 : 운영체제(OS), 웹 서버 및 WAS 운용을 위한 서버 프로그램, DBMS 등
- 개발 소프트웨어의 종류
  - 요구사항 관리 도구
  - 설계/모델링 도구
  - 구현 도구
  - 빌드 도구
  - 테스트 도구
  - 형상 관리 도구

<br>

#### [4] 웹 서버(Web Server)의 기능

|기능|내용|
|:---:|:---:|
|HTTP/HTTPS 지원|브라우저로부터 요청을 받아 응답할 때 사용|
|통신 기록(Communication Log)|요청들을 로그 파일로 기록|
|정적 파일 관리(Managing Static Files)|정적 파일(HTML, CSS, 이미지 등)을 관리|
|대역폭 제한(Bandwidth Throttling)|네트워크 포화 방지를 위해 응답 속도 제한|
|가상 호스팅(Virtual Hosting)|하나의 서버에서 여러 도메인 관리|
|인증(Authentication)|합법적인 사용자인지 확인|

<br>

#### [5] 개발 언어의 선정 기준

|기준|내용|
|:---:|:---:|
|적정성|소프트웨어의 목적에 적합|
|효율성|작성 및 구현이 효율적|
|이식성|다양한 시스템 및 환경에 적용 가능|
|친밀성|개발자들의 이해도와 활용도가 높음|
|범용성|다른 개발 사례가 존재, 여러 분야에서 활용중|

<br>
<br>

### 63. 소프트웨어 아키텍처
#### [1] 소프트웨어 아키텍처
- **소프트웨어 아키텍처** : **소프트웨어를 구성하는 요소들 간의 관계를 표현하는 시스템의 구조 또는 구조체**

<br>

#### [2] 모듈화(Modularity)
- **모듈화** : **시스템의 기능들을 모듈 단위로 나누는 것**

<br>

#### [3] 추상화(Abstraction)
- **추상화** : **전체적이고 포괄적인 개념을 설꼐한 후 차례로 세분화하여 구체화시켜 나가는 것**

- 추상화의 유형
  - 과정 추상화 : 자세한 수행 과정을 전반적인 흐름으로만 추상화
  - 데이터 추상화 : 세부 속성을 대신하는 표현으로 추상화
  - 제어 추상화 : 이벤트의 절차를 대신하는 표현으로 추상화

<br>

#### [4] 단계적 분해(Stepwise Refinement)
- **단계적 분해** : **문제를 상위의 중요 개념으로부터 하위의 개념으로 구체화시키는 분할 기법**

<br>

#### [5] 정보 은닉(Information Hiding)
- **정보 은닉** : **모듈 내부에 포함된 절차와 자료들의 정보가 감추어져 다른 모듈이 접근하거나 변경하지 못하도록 하는 기법**

<br>

#### [6] 상위 설계와 하위 설계

||상위 설계|하위 설계|
|:---:|:---:|:---:|
|별칭|아키텍쳐 설계, 예비 설계|모듈 설계, 상세 설계|
|설계 대상|시스템의 전체적인 구조|시스템의 내부 구조 및 행위|
|세부 목록|구조, DB, 인터페이스|컴포넌트, 자료 구조, 알고리즘|

<br>

#### [7] 소프트웨어 아키텍처의 품질 속성
- 품질 평가 요소의 종류
  - 시스템 측면 : 성능, 보안, 가용성, 기능성, 사용성, 변경 용이성, 확장성 등
  - 비즈니스 측면 : 시장 적시성, 비용과 혜택, 예상 시스템 수명, 목표 시장, 공개 일정 등
  - 아키텍처 측면 : 개념적 무결성, 정확성, 완결성, 구축 가능성, 변경성, 시험성 등

<br>

#### [8] 소프트웨어 아키텍처의 설계 과정
- (1) 설계 목표 설정

- (2) 시스템 타입 결정

- (3) 아키텍처 패턴 적용

- (4) 서브시스템 구체화

- (5) 검토

<br>

#### [9] 협약(Contract)에 의한 설계
- **협약에 의한 설계** : **컴포넌트를 설계할 때 클래스에 대한 여러 가정을 공유할 수 있도록 명세한 것**

- 명세에 포함된 조건

|조건|내용|
|:---:|:---:|
|선행 조건(Precondition)|오퍼레이션이 호출되기 전에 참이 되어야 할 조건|
|후행 조건(Postcondition)|오퍼레이션이 수행된 후 만족되어야 할 조건|
|불변 조건(Invariant)|오퍼레이션이 실행되는 동안 항상 만족되어야 할 조건|

<br>
<br>

### 64. 아키텍처 패턴
#### [1] 아키텍처 패턴
- **아키텍처 패턴** : **아키텍처를 설계할 때 참조할 수 있는 전형적인 해결 방식 또는 예제**

<br>

#### [2] 레이어 패턴(Layers Pattern)
- **레이어 패턴** : **시스템을 계층으로 구분하여 구성하는 고전적인 방법의 패턴**

- 예 : OSI 참조 모델

<br>

#### [3] 클라이언트-서버 패턴(Client-Server Pattern)
- **클라이언트-서버 패턴** : **하나의 서버 컴포넌트와 다수의 클라이언트 컴포넌트로 구성되는 패턴**

<br>

#### [4] 파이프-필터 패턴(Pipe-Filter Pattern)
- **파이프-필터 패턴** : **데이터 스트림 절차의 각 단계를 필터로 캡슐화하여 파이프를 통해 전송하는 패턴**

- 예 : UNIX의 쉘(Shell)

<br>

#### [5] 모델-뷰-컨트롤러 패턴(Model-View-Controller Pattern)
- **모델-뷰-컨트롤러 패턴** : **서브시스템을 모델, 뷰 컨트롤러로 구조화하는 패턴**

<br>

#### [6] 기타 패턴

|종류|내용|
|:---:|:---:|
|마스터-슬레이브 패턴(Master-Slave Pattern)|슬레이브 컴포넌트에서 처리된 결과물을 다시 돌려받는 방식<br>예 : 장애 허용 시스템, 병렬 컴퓨팅 시스템|
|브로커 패턴(Broker Pattern)|원하는 서비스와 특성을 브로커 컴포넌트에 요청하면 브로커가 적절한 컴포넌트와 사용자를 연결해주는 방식<br>예 : 분산 환경 시스템|
|피어-투-피어 패턴(Peer-to-Peer Pattern)|피어(Peer)라고 불리는 하나의 컴포넌트가 클라이언트이자 서버 역할을 동시에 수행하는 방식<br>예 : 파일 공유 네트워크|
|이벤트-버스 패턴(Event-Bus Pattern)|특정 채널에 이벤트 메시지를 발행(Publish)하면 채널을 구독(Subscribe)한 리스너(Listener)들이 이벤트를 수신 및 처리하는 방식<br>예 : 알림 서비스|
|블랙보드 패턴(Blackboard Pattern)|모든 컴포넌트들이 공유 데이터 저장소와 블랙보드 컴포넌트에 접근 가능한 패턴<br>예 : 음성 인식, 차량 식별, 신호 해석|
|인터프리터 패턴(Interpreter Pattern)|문법을 정의하고 해석하는 패턴<br>예 : 번역기, 컴파일러, 인터프리터|

<br>
<br>

### 65. 객체지향(Object-Oriented)
#### [1] 객체지향
- **객체지향** : **각 요소들을 객체(Object)로 만든 후, 객체들을 조립해서 소프트웨어를 개발하는 기법

<br>

#### [2] 객체(Object)
- **객체** : **데이터와 이를 처리하기 위한 함수를 묶어 놓은 소프트웨어 모듈**

<br>

#### [3] 클래스(Class)
- **클래스** : **공통된 속성과 연산을 갖는 객체의 집합**

<br>

#### [4] 메시지(Message)
- **메시지** : **객체들 간의 상호작용을 하는데 사용되는 수단**

<br>

#### [5] 캡슐화(Encapsulation)
- **캡슐화** : **외뷍서의 접근을 제한하기 위해 인터페이스를 제외한 세부 내용을 은닉하는 것**

<br>

#### [6] 상속(Inheritance)
- **상속** : **상위 클래스의 모든 속성과 연산을 하위 클래스가 물려받는 것**

<br>

#### [7] 다형성(Polymorphism)
- **다형성** : **하나의 메시지에 대해 각각의 객체가 가지고 있는 고유한 방법으로 응답할 수 있는 능력**

<br>

#### [8] 연관성(Relationship)
- **연관성** : **두 개 이상의 객체들이 상호 참조하는 관계**

|종류|의미|특징|
|:---:|:---:|:---:|
|`is a member of`|연관성(Association)|2개 이상의 객체가 상호 관련|
|`is instance of`|분류화(Classification)|동일한 타입의 특성을 갖는 객체를 그룹화|
|`is a part of`|집단화(Aggregation)|관련 있는 객체들을 묶어 하나의 상위 객체로 표현|
|`is a`|일반화(Generalization)<br>특수화/상세화(Specialization)|공통적인 성질들로 추상화<br>상위 객체를 구체화|

<br>
<br>

### 66. 객체지향 분석 및 설계
#### [1] 객체지향 분석(OOA; Object-Oriented Analysis)
- **객체지향 분석** : **사용자의 요구사항과 관련된 객체, 속성, 연산, 관계 등을 정의하여 모델링하는 작업**

<br>

#### [2] 객체지향 분석의 방법론

|종류|핵심|
|:---:|:---:|
|Rumbaugh(럼바우) 방법|분석 활동을 객체 모델, 동적 모델, 기능 모델로 나누어 수행|
|Booch(부치) 방법|미시적(Micro) 개발 프로세스와 거시적(Macro) 개발 프로세스 모두 사용|
|Jacobson 방법|유스케이스(Use Case)를 강조|
|Coad와 Yourdon 방법|E-R 다이어그램을 사용|
|Wirfs-Brock 방법|고객 명세서를 평가|

<br>

#### [3] 럼바우(Rumbaugh) 분석 기법
- **럼바우 분석 기법** : **모든 소프트웨어 구성 요소를 그래픽 표기법을 이용하여 모델링하는 기법**

|분석 모델|설명|
|:---:|:---:|
|객체 모델링(Object Modeling)|정보 모델링이라고도 하며, 객체 관계를 **객체 다이어그램**으로 표현|
|동적 모델링(Dynamic Modeling)|객체의 동적인 상태 변화를 **상태 다이어그램**으로 표현|
|기능 모델링(Functional Modeling)|프로세스들 간의 자료 흐름을 **자료 흐름도(DFD)**로 표현|

<br>

#### [4] 객체지향 설계 원칙
- **객체지향 설계 원칙** : **변경이나 확장에 유연한 시스템을 설계하기 위해 지켜져야 할 원칙**

- 객체지향 설계 원칙의 종류 (SOLID 원칙)

|종류|내용|
|:---:|:---:|
|단일 책임 원칙(SRP)|객체는 단 하나의 책임만|
|개방-폐쇄 원칙(OCP)|기존 코드를 변경하지 않고 기능을 추가|
|리스코프 치환 원칙(LSP)|자식 클래스는 최소한 부모 클래스의 기능은 수행|
|인터페이스 분리 원칙(ISP)|사용하지 않는 인터페이스와 의존 관계를 맺지 않도록 분리|
|의존 역전 원칙(DIP)|의존 관계 성립 시 추상성이 높은 클래스와 의존 관계를 맺도록 설계|

<br>
<br>

### 67. 모듈
#### [1] 모듈(Module)
- **모듈** : **모듈화를 통해 분리된 시스템의 각 기능**

<br>

#### [2] 결합도(Coupling)
- **결합도** : **모듈 간의 상호 의존성 정도**

- 결합도는 약할수록 좋고, 강할수록 나쁘다.

- 결합도의 종류와 강도(강한 결합도 → 약한 결합도)
  - (1) 내용 결합도 : 다른 모듈의 내부 자료를 직접 참조
  - (2) 공통 결합도 : 공통 데이터 영역을 공유
  - (3) 외부 결합도 : 외부의 다른 모듈에서 변수를 참조
  - (4) 제어 결합도 : 제어를 위한 신호나 요소를 전달
  - (5) 스탬프 결합도 : 모듈 간 인터페이스로 자료 구조를 전달
  - (6) 자료 결합도 : 모듈 간 인터페이스로 단순 자료를 전달

<br>

#### [3] 응집도(Cohesion)
- **응집도** : **모듈 내부의 구성 요소들이 서로 관련되어 있는 정도**

- 응집도는 강할수록 좋고, 약할수록 나쁘다.

- 응집도의 종류와 강도(약한 응집도 → 강한 응집도)
  - (1) 우연적 응집도 : 서로 관련이 없음
  - (2) 논리적 응집도 : 유사한 성격 또는 특정 형태로 분류
  - (3) 시간적 응집도 : 특정 시간에 처리되는 기능들을 모음
  - (4) 절차적 응집도 : 구성 요소들이 순차적으로 수행됨
  - (5) 교환적 응집도(통신적 응집도) : 동일한 입력과 출력
  - (6) 순차적 응집도 : 출력 데이터를 다음 모듈의 입력으로 사용
  - (7) 기능적 응집도 : 모든 기능 요소들이 단일 목적을 수행

<br>

#### [4] 팬인(Fan-in) / 팬아웃(Fan-out)
- **팬인(Fan-in)** : **어떤 모듈을 제어하는 모듈의 수**
- **팬아웃(Fan-out)** : **어떤 모듈에 의해 제어되는 모듈의 수**

<br>

#### [5] N-S 차트(Nassi-Shneiderman Chart)
- **N-S 차트** : **논리의 기술에 중점을 두고 도형을 이용해 표현하는 방법**

<br>

  - (3) 알고리즘 구현

#### [2] IPC(Inter-Process Communication)
- **IPC** : **모듈 간 통식 방식을 구현하기 위해 사용되는 대표적인 프로그래밍 인터페이스 집합**

- IPC의 대표 메소드 5가지

|메소드|특징|
|:---:|:---:|
|Shared Memory|공유 메모리를 통해 프로세스가 통신|
|Socket|네트워크 소켓을 이용하여 프로세스 간 통신|
|Semaphores|공유 자원에 대한 접근 제어로 통신|
|Pipes & Named Pipes|Pipe(선입선출 메모리)로 통신|
|Message Queueing|메시지 큐를 통해 통신|

<br>

#### [4] 테스트 케이스(Test Case)

  - 출력 명세서(Output Specification)

  - 의존성 기술(Inter-case Dependencies)

### 70. 코드
#### [1] 코드
- **코드** : **자료의 분류·조합·집계·추출을 용이하게 하기 위해 사용하는 기호**

<br>

#### [2] 코드의 주요 기능
- 코드의 주요 기능
  - 식별 기능
  - 분류 기능
  - 배열 기능
  - 표준화 기능
  - 간소화 기능

<br>

#### [3] 코드의 종류

|종류|내용|
|:---:|:---:|
|순차 코드(Sequential Code)|차례로 일련번호를 부여하는 방법<br>예 : `1`, `2`, `3`|
|블록 코드(Block Code)|공통성이 있는 것끼리 블록으로 구분하고 블록 내에서 일련번호를 부여하는 방법<br>예 : `1001~1100`, `1101~1200`|
|10진 코드(Decimal Code)|대상 항목을 0~9까지 10진 분할하고 다시 재귀적으로 10진 분할하는 방법(도서 분류식)<br>예 : `1000`, `1100`, `1110`|
|그룹 분류 코드(Group Classification Code)|대분류, 중분류, 소분류 등으로 구분하고 각 그룹 내에서 일련번호를 부여하는 방법<br>예 : `1-01-001`, `2-01-001`|
|연상 코드(Mnemonic Code)|대상 항목의 명칭이나 약호와 관계있는 숫자, 문자, 기호를 이용하여 코드화하는 방법<br>예 : `TV-40`, `L-15-220`|
|표의 숫자 코드(Significant Digit Code)|길이, 넓이, 부피, 지름, 높이 등의 물리적 수치를 그대로 코드화하는 방법<br>예 : `120-720-1500`|
|합성 코드(Combined Code)|두 가지 이상의 코드화 방법을 조합하여 코드화하는 방법|

<br>

### 71. 디자인 패턴
#### [1] 디자인 패턴(Design Pattern)
- **디자인 패턴** : **모듈 간의 관계 및 인터페이스를 설계할 때 참조할 수 있는 전형적인 해결 방식 또는 예제**

<br>

#### [2] 생성 패턴(Creational Pattern)
- **생성 패턴** : **클래스나 객체의 생성과 참조 과정을 정의하는 패턴
  - 추상 팩토리(Abstract Factory) : 인터페이스를 통해 추상적으로 표현
  - 빌더(Builder) : 작게 분리된 인스턴스를 건축하듯이 조합
  - 팩토리 메소드(Factory Method) : 객체 생성을 서브 클래스에서 처리하도록 분리 및 캡슐화
  - 프로토타입(Prototype) : 원본 객체를 복제하는 방법
  - 싱글톤(Singleton) : 클래스 내에서 인스턴스가 하나뿐임을 보장

<br>

#### [3] 구조 패턴(Structural Pattern)
- **구조 패턴** : **클래스나 객체를 조합하여 더 큰 구조를 만드는 패턴**
  - 어댑터(Adapter) : 기존 클래스를 이용하도록 인터페이스를 변환
  - 브리지(Bridge) : 구현부에서 추상층을 분리
  - 컴포지트(Composite) : 객체들을 트리 구조로 구성
  - 데코레이터(Decorator) : 다른 객체들을 덧붙이는 결합을 통해 기능 확장
  - 퍼사드(Facade) : 더 상위에 Wrapper 객체를 만들어 단순화된 인터페이스 제공
  - 플라이웨이트(Flyweight) : 인스턴스를 매번 생성하지 않고 가능한 공유
  - 프록시(Proxy) : 객체 사이에서 인터페이스 역할을 수행, a.k.a 대리자

<br>

#### [4] 행위 패턴(Behavioral Pattern)
- **행위 패턴** : **클래스나 객체들이 서로 상호작용하는 방법이나 책임 분배 방법을 정의**
  - 책임 연쇄(Chain of Responsibility) : 요청 처리 실패 시 다음 객체로 전달
  - 커맨드(Command) : 요청을 객체의 형태로 캡슐화
  - 인터프리터(Interpreter) : 언어에 문법 표현을 정의
  - 반복자(Iterator) : 접근이 잦은 객체에 대해 동일한 인터페이스 제공
  - 중재자(Mediator) : 복잡한 상호작용을 캡슐화
  - 메멘토(Memento) : 특정 시점에서의 객체 내부 상태를 객체화
  - 옵저버(Observer) : 객체 상태 변화 시 다른 객체에 전달
  - 상태(State) : 객체의 상태에 따라 행동을 변경
  - 전략(Strategy) : 동일한 계열의 알고리즘들을 개별적으로 캡슐화
  - 템플릿 메소드(Template Method) : 상위 클래스에서 골격을 정의하고 하위 클래스에서 세부 처리를 구체화
  - 방문자(Visitor) : 각 클래스의 데이터 구조에서 처리 기능을 분리

<br>

### 74. 배치 프로그램
#### [1] 배치 프로그램(Batch Program)
- **배치 프로그램** : **여러 작업들을 미리 정해진 일련의 순서에 따라 일괄적으로 처리하도록 만든 프로그램**

- 배치 프로그램의 필수 요소

|요소|내용|
|:---:|:---:|
|대용량 데이터|대량의 데이터 처리가 가능|
|자동화|사용자의 개입 없이 수행|
|견고성|중단되는 일 없이 수행|
|안정성/신뢰성|오류가 발생하면 추적할 수 있음|
|성능|다른 응용프로그램 수행 방해 없이 지정된 시간 내에 처리|

<br>

#### [2] 배치 스케쥴러(Batch Scheduler)
- **배치 스케쥴러** : **일괄 처리(Batch Processing) 작업이 설정된 주기에 맞춰 자동으로 수행되도록 지원해주는 도구**

- 배치 스케쥴러의 종류
  - 스프링 배치(Spring Batch)
  - Quartz
  - Cron
